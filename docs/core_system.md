# Core System & Initialization Architecture (`core_system.md`)

This document provides an exhaustive technical specification of the **Midum Core System**, covering the startup initialization sequence, event loop management, tool dispatching architecture, memory management persistence layers, and system-wide state handling.

---

## 1. System Initialization & Startup Sequence

When `midum_pkg` initializes, the bootstrap routine establishes the foundational runtime environment:
1. **Environment Verification**: Validates Python environment compatibility (Python 3.10+), checks virtual environment bindings, and loads environment variables from local configuration files and secret stores.
2. **Directory Tree Bootstrapping**: Ensures required runtime directories (`storage/`, `docs/`, temporary asset caches) exist with proper POSIX/NTFS read-write permissions.
3. **Memory Loading**: Reads persistent memory stores into active context:
   - `storage/master.md`: Global behavioral rules and user preferences.
   - `storage/project.md`: Current project scope, objectives, and domain knowledge.
   - `storage/session.md`: Ephemeral session variables and working logs.
4. **MCP Server Auto-Connection**: Parses `storage/mcp_servers.json` and establishes persistent connections (stdio, HTTP, SSE) to registered Model Context Protocol servers.
5. **Supervisor and Sub-Agent Daemon Start**: Initializes the primary event loop and background thread worker pools.

## 2. The Main Reasoning & Execution Loop

Midum operates on an iterative **Perception-Reasoning-Action-Observation** loop:

```
[User Input / Event] 
       │
       ▼
[Context Assembler] (Injects Master, Project, Session, Skills)
       │
       ▼
[Active LLM Brain] (Generates Thought & Tool Call / Response)
       │
       ├─────────────────────────┐ (If Tool Call)
       ▼                         ▼
[Tool Dispatcher]         [Text Response]
       │                         │
       ▼                         ▼
[Execution Sandbox]       [Output to User]
       │
       ▼
[Observation Capture]
       │
       └─────► [Loop back to Context Assembler if Action Loop active]
```

### Action Loop Mode (`start_action_loop`)
When complex tasks require back-to-back operations without pausing for user confirmation between steps, the system enters the continuous action loop. 
* The model emits tool calls sequentially.
* The execution harness runs each tool, captures STDOUT/STDERR or UI inspection results, and feeds the observation back into the active context.
* Execution terminates only upon calling `stop_action_loop` or encountering an unresolvable blocker.

## 3. Memory Subsystem & Persistence Layers

Midum utilizes a hierarchical Markdown-based memory architecture located under `storage/`:

| Memory Target | File Path | Scope & Persistence | Purpose |
|---------------|-----------|---------------------|---------|
| `master` | `storage/master.md` | Permanent / Global | Stores core user instructions, behavioral constraints, formatting rules, and global overrides added via `add_instruction`. |
| `project` | `storage/project.md` | Project-specific | Captures current development goals, architecture notes, and domain context. |
| `session` | `storage/session.md` | Ephemeral (Session) | Active working notes, scratchpad for partial computations, and short-term variables. |
| `response_memory` | `storage/response_memory.md` | Multi-step Task | Automated task breakdown checklists (`write_response_memory`, `append_response_memory`) wiped upon goal completion. |

## 4. Tool Dispatching & Execution Engine

The Tool Dispatcher serves as the centralized gateway between LLM intent and system execution:
1. **Schema Validation**: Every tool call generated by an LLM is intercepted and validated against its corresponding JSON schema (native tool definitions, UIA automation bindings, or MCP tool descriptors).
2. **Permission & Safety Guardrails**: Sensitive operations (file deletion, terminal execution, outbound network mutations, Discord broadcasting) trigger safety checks and mandatory user approval modals (`ask_user_approval`) when configured.
3. **Sandbox Isolation**: Python code snippets (`execute_python_code`) run in isolated subprocess interpreters with strict execution timeouts (default 15s, hard cap 60s). Terminal commands (`execute_terminal_command`) execute within PowerShell with controlled working directories.
4. **Structured Error Handling**: Tool execution failures catch tracebacks, normalize error strings, and return clean diagnostic payloads to the LLM reasoning loop for self-correction.

---

## 5. Configuration and State Management

System configuration is managed dynamically through runtime APIs and persisted JSON files:
* **Paths Registry (`paths.md`)**: Maps application labels (e.g., `'Blender'`, `'Chrome'`) to absolute filesystem paths, queryable via `list_paths_indexed` and `get_path`.
* **Skills Library (`skills/`)**: Stores domain-specific operational playbooks and Markdown skill files loaded on demand.
* **MCP Registry (`storage/mcp_servers.json`)**: Maintains connection metadata for all active Model Context Protocol servers.
